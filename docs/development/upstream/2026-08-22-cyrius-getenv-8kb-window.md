# cyrius — `getenv` silently ignores anything past 8 KB of environment

- **Filed by:** owl (1.4.6 audit, INFO-002)
- **Component:** `lib/io.cyr` — `fn getenv(name)`
- **Severity:** low impact per call site, but it fails *silently* and it
  affects a documented user-facing control (`NO_COLOR`)
- **Status:** open — not worked around downstream, see §Why owl did not patch it

## What happens

`getenv` reads `/proc/self/environ` into a fixed 8 KB buffer and scans only
what fits:

```
    var buf[8192];
    var fd = file_open("/proc/self/environ", 0, 0);
    if (fd < 0) { return 0; }
    var n = file_read(fd, &buf, 8192);
```

Any variable whose entry begins past byte 8192 is invisible. There is no
error, no truncation signal, and no way for a caller to tell "unset" from
"beyond the window" — both return 0.

An 8 KB environment is not exotic. A single `PATH` on a developer machine,
a CI runner's injected secrets, or one large `LS_COLORS` can push later
variables out of reach.

## Measured, in owl

`NO_COLOR` is the clearest demonstration because its whole contract is
"any non-empty value disables colour":

| environment | `NO_COLOR=1` set? | ESC bytes owl wrote |
|---|---|---|
| small | yes | **0** — honoured |
| one var of 20,000 bytes | yes | **18** — silently ignored |

Reproduced with `owl --paging=never FILE` under a PTY on owl 1.4.6,
cyrius 6.5.35.

The same applies to every other environment input owl reads: `OWL_PAGER`,
`PAGER`, `HOME`, `XDG_CONFIG_HOME`, `OWL_CONFIG`. In owl's case a missed
`HOME`/`XDG_CONFIG_HOME` means the user's config and themes silently do not
load.

## Why this is worth fixing rather than documenting

The failure is invisible from both sides. The caller cannot detect it, and
the user sees a tool ignoring a variable they definitely set. For
`NO_COLOR` specifically there is a published cross-tool convention
(no-color.org) that consumers are expected to honour unconditionally.

## Suggested shapes, roughly in order of preference

1. **Size the read to the actual environment.** `/proc/self/environ` is not
   seekable to a size, but the block can be read in a loop into a growing
   `alloc` buffer until EOF. Cost is one allocation on first call; the
   result can be cached for the process, which would also make repeated
   `getenv` calls cheaper than the current re-read-per-call.
2. **Cache and index once.** Parse the environment into a hashmap on first
   use. Turns N lookups from N file reads into one.
3. **At minimum, signal truncation.** If the read fills the buffer exactly,
   the environment is probably longer; a distinguishable return (or a
   `getenv_ok`-style companion) lets a caller decide.

Option 1 or 2 also removes the `#ifndef CYRIUS_TARGET_AGNOS` buffer that
the current code notes is deliberately kept out of the agnos frame for
stack reasons (`CHANGELOG [6.1.12]`) — a heap buffer has no such
constraint.

## Why owl did not patch it downstream

`lib/` is materialised from `[deps]` and regenerated by `cyrius deps`;
owl's CLAUDE.md forbids editing it. owl could carry a private `getenv`,
but that would diverge from every other cyrius consumer and leave the same
bug in place for all of them — the fix belongs here.

## Note for the reporter's own posture

owl's escape-stripping guarantee does **not** depend on this. `_strip_active()`
keys off `g_want_color`, which resolves from TTY detection rather than the
environment, so a truncated environment can only fail to *enable*
`NO_COLOR` — erring toward more decoration, never toward passing
file-origin escapes through to a terminal.

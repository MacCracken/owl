# owl — P(−1) Audit, Hardening and Repair

- **Date:** 2026-08-22
- **Version audited:** 1.4.5 (commit `5506ddb`)
- **Version shipping the repairs:** 1.4.6
- **Source under review:** `src/main.cyr`, `src/lang.cyr`, `src/theme.cyr`,
  `src/pager.cyr`, `src/vcs.cyr`, `src/config.cyr` (3,906 lines)
- **Excluded from scope:** vendored `lib/` — `lib/vyakarana.cyr` (audited by
  that project; see its `docs/audit/`), `lib/sit.cyr` (ditto, most recently
  its 2026-08-18 deep audit), and the Cyrius stdlib. owl's posture depends on
  their correctness. Where a defect's root cause landed there it is filed
  below as INFO with the upstream owner named, not repaired locally.
- **Methodology:** exhaustive internal surface walk — every `alloc()`, every
  `var buf[N]`, every `syscall`, every `getenv`, every parser, every path
  that copies attacker-influenced bytes — followed by a working repro for
  each candidate before it was accepted as a finding. Two candidates were
  discarded at the repro stage (see §Discarded).

## Findings

### FINDING-006 — An unterminated escape sequence silently suppresses the rest of the file — **HIGH**

**Location:** `src/main.cyr` — `_emit_file_byte`.

**Issue.** The escape-strip classifier introduced for FINDING-001 is a state
machine with no bound on how long a sequence may run. Once it enters the CSI
state (`ESC [`) it stays there until a byte in `0x40–0x7E` arrives; the OSC /
DCS / APC / PM / SOS state waits for BEL or ST. Every byte consumed on the way
is dropped. A file whose remaining bytes never contain a terminator therefore
has **all** of them dropped — and the caller skips the dropped byte entirely,
including the `g_line_no` increment, so a swallowed newline is a line the
gutter never counts.

Two consequences, both reachable with a **2-byte** file prefix:

1. **Arbitrary content is hidden from the viewer.** A 442-byte, 40-line file
   rendered as **0 bytes** — the header frame drew, one empty line-1 gutter
   drew, the closing rule drew, exit status 0. Nothing signalled that the
   file had any content at all.
2. **Line numbers stop corresponding to the file.** Where a terminator did
   eventually arrive, everything up to it was consumed including newlines, so
   the gutter labelled file line 2 as "1" and every subsequent number was off
   by the number of swallowed newlines.

This is the hidden-content class (cf. CVE-2021-42574, "Trojan Source" —
content that renders differently from what it is). It is worse than usual
here because owl's entire contract is *show me this file*, and README §Agent
usage documents owl as the tool an agent reads source with: a repo file
carrying an unterminated CSI renders as empty to a reviewer while `cat`,
`git` and every editor show the real bytes.

**Reachable by default.** `_strip_active()` returns 1 whenever output is
decorated and coloured, which is the default for `owl FILE` on a terminal. No
flag is required.

**Repro** (`ESC [` followed by digits and newlines only — no byte in the file
can terminate a CSI):

```
printf '\033[' > f.txt; for i in $(seq 40); do printf '1234567890\n' >> f.txt; done
cat f.txt | wc -c        # 442
owl -p f.txt | wc -c     # 442  (plain mode is untouched)
owl f.txt                # renders NOTHING — 0 content bytes, exit 0
```

Confirmed under a real PTY with a bare `owl f.txt` (no flags): 969 bytes of
frame and gutter, zero bytes of file content.

**Fix.** Two independent bounds in `_emit_file_byte`, either of which
abandons the sequence and **emits** the byte that tripped it:

- **A newline terminates any in-progress sequence.** No CSI, OSC, DCS, APC,
  PM or SOS form admits a raw LF, and terminals abandon on one, so this
  costs nothing in stripping fidelity. It bounds suppression to a single
  line and — because the LF is now emitted — keeps `g_line_no` in step with
  the file.
- **A byte ceiling, `ESC_MAX_LEN = 256`.** Covers the no-newline case. Far
  past any real sequence; owl drops OSC bodies wholesale regardless.

**Verification.** The 442-byte file now renders 430 bytes (the 12 dropped are
`ESC [` plus the 10 digits before the first LF, which genuinely are on that
line), and `-n` labels the first payload line 2, matching the file. Stripping
fidelity re-verified separately: a file carrying OSC 52 (clipboard write),
CSI SGR, OSC 0 + ST, DCS and `ESC 7` renders with **zero** ESC bytes
surviving. Gated in `scripts/smoke.sh`; both halves of the gate fail against
the 1.4.5 binary.

### FINDING-007 — Heap overflow building the config path from the environment — **MEDIUM**

**Location:** `src/config.cyr` — `_config_resolve_path`.

**Issue.** Both candidate paths were built by appending an environment
variable into a **fixed** `alloc(1024)`:

```
var buf = alloc(1024);
o = _cfg_append_n(buf, o, xdg, strlen(xdg));   # unbounded
o = _cfg_append(buf, o, "/owl/config.cyml");
store8(buf + o, 0);
```

`$XDG_CONFIG_HOME` past ~1007 bytes (or `$HOME` past ~999) writes off the end
of the allocation, with both the length and the content chosen by whoever
sets the variable. `main.cyr`'s equivalent joiner (`_resolve_user_grammars_dir`)
already sized its allocation from the operands; this one did not.

**Repro.** The overflow is not observable through the binary — it lands in
unused bump arena (a 256 MB anonymous mmap chunk), so the process exits 0.
It was confirmed instead with a canary program using the two helpers
verbatim, `alloc(1024)` followed by a 64-byte canary allocation:

```
bytes written into the 1024-byte buffer: 2017
canary bytes clobbered (of 64):            64
RESULT: heap overflow CONFIRMED
```

Against the repaired `_cfg_join`, the same program reports a 2016-byte path
written and **0** canary bytes clobbered.

**Severity.** MEDIUM, not HIGH: the environment is process input, but in
owl's current startup order the overflow reaches only arena that has not been
handed out yet, so it is memory corruption without a demonstrated victim.
That is a property of the call order, not of the code — it is one reordering
away from mattering.

**Fix.** A single `_cfg_join(base, suffix)` that sizes the allocation from
`strlen(base) + strlen(suffix) + 1`, checks the `alloc`, and refuses a base
longer than `PATH_MAX_SANE` (4096) — a path that long cannot name a real
file, so resolution falls through to the next candidate. That fallback is
what the smoke gate pins, since it is the externally visible half of the fix.

### FINDING-008 — Unvalidated theme colour overruns two fixed buffers — **MEDIUM**

**Location:** `src/theme.cyr` — `_theme_parse_int` / `_theme_apply` /
`_u16_to_ascii` / `ansi_fg`.

**Issue.** `_theme_parse_int` accumulates `v = v * 10 + digit` with no range
check, and `_theme_apply` stored the result straight into the colour globals.
Those reach `ansi_fg`, which builds `\e[38;5;<n>m` in a **16-byte** buffer
via `_u16_to_ascii`, which formats into an **8-byte** buffer by decrementing
an index from 7. Neither is sized for more than three digits.

A theme file line `lineno_color = 999999999999999999` (18 digits) therefore:

- underflows `nbuf[8]` — `pi` walks from 7 down to −10, writing 10 bytes
  *before* the buffer;
- overruns `buf[16]` — the terminating `m` is stored at offset 25, ten bytes
  past the end;
- discloses the overrun back out, since `syscall(1, 1, &buf, off)` then
  writes `off` bytes from a 16-byte buffer.

Theme files come from `$XDG_CONFIG_HOME/owl/themes/` or
`$HOME/.config/owl/themes/`. That is user configuration rather than remote
input, but colour themes are exactly the kind of file people copy from a
gist, and config parsing was in scope for the 2026-04-23 audit on the same
reasoning.

**Repro.** With `lineno_color` set to 18 nines, `owl -n --color=always
--theme=<name>` emitted `\e[38;5;999999999999999999m` — a **26-byte** escape
out of a 16-byte buffer.

**Fix.** Three layers:

- `_theme_color_ok` rejects anything outside `-1..255` at parse time; a bad
  line is ignored exactly like every other bad line in this parser.
- `header_color` / `lineno_color` additionally reject `-1`. Unlike the token
  and VCS colours, `main.cyr` never tests these for `-1` before calling
  `ansi_fg`, so "no colour" is not a meaningful value for them — previously
  it emitted a malformed `\e[38;5;m`.
- `_u16_to_ascii` clamps to `0..255` regardless of caller. Its only caller is
  `ansi_fg`, whose buffer is sized for three digits; "the caller validated
  it" is not a bound this function may assume.

After the fix the longest SGR any theme value can produce is 12 bytes.

### FINDING-009 — Pager env forwarding publishes an unterminated entry — **LOW**

**Location:** `src/pager.cyr` — `start_pager`.

**Issue.** The child reads `/proc/self/environ` into a fixed 16 KB buffer and
walks it for NUL-separated entries. An environment larger than that truncates
mid-entry, and the walk still published a pointer to that final, unterminated
entry. `execve` then reads past `envbuf` — which, being an oversized local, is
placed in shared globals — copying adjacent memory into the child's
environment.

**Severity.** LOW. The reader is a pager the user chose, in a process they
control, so this leaks their own memory to their own program; and it needs a
>16 KB environment to trigger.

**Fix.** Locate the last NUL in the buffer; accept an entry only if it starts
at or before it, which is exactly the condition for it being terminated
within the buffer. This is provably a subset removal — for any entry ending
at a NUL, that NUL is at or before the last one, so every terminated entry
still forwards. Verified: 46 entries forwarded with `PATH` present on a
normal environment, unchanged from before.

### FINDING-010 — Unbounded tab width — **LOW**

**Location:** `src/main.cyr` — `set_tabs`.

**Issue.** `set_tabs` validated that every byte was a digit and then took
`atoi` with no ceiling, reachable from both `--tabs=` and a `tabs =` config
line. Each literal TAB expands to that many spaces, so a large value wedges
the process — or writes unboundedly when stdout is a file. A 20-digit value
also overflows `i64` inside `atoi` before any range check on the result could
see it.

**Fix.** Reject more than 3 digits *before* `atoi` (so the overflow cannot
launder a value past a check applied afterwards), then bound the result to
`0..TABS_MAX` (64). A tab stop wider than a terminal is already meaningless.

### FINDING-011 — `alloc()` return unchecked at every call site — **LOW**

**Location:** all six modules (~27 sites).

**Issue.** `alloc()` returns 0 on failure (`size <= 0`, `size > ALLOC_MAX`, or
a failed chunk mmap) and owl checked none of its call sites. The failure mode
is a write through a null pointer. The largest request owl makes is
`alloc(HIGHLIGHT_MAX + 1)` — 16 MB, twice in `render_path`. vyakarana's 2.3.4
audit closed the identical class upstream.

**Fix.** Guards on the load-bearing sites, each degrading to an already-existing
path rather than inventing a new one: the two highlight buffers fall back to
plain streaming (what every other "cannot highlight" condition does), the
`BUFSIZE` read buffers return an I/O error, the config and theme file buffers
return "no config"/"no theme", and `_user_ext_init` / `_user_theme_init` now
propagate failure to callers that previously ignored their return value.

### FINDING-012 — VCS marker table sized from an unvalidated backend value — **LOW**

**Location:** `src/vcs.cyr` — `vcs_compute_markers`.

**Issue.** `max_line` is the highest new-side line number in sit's edit
script, and the marker table allocation is sized directly from it, then
zeroed in a loop of that length. sit reads `.git/` repositories, which owl
may be pointed at for a repo cloned from anywhere — the threat model sit's
own 2026-08-17 audit names explicitly ("owl/thoth report on repos cloned from
untrusted remotes"). A corrupt object yielding a nonsense line count becomes a
nonsense allocation and a long zeroing loop, or a null-pointer write if the
allocation fails.

**Fix.** Fail closed above `VCS_MAX_LINES` (16,777,216 — one byte per line,
so a 16 MB ceiling on the table) and check the `alloc`.

**A defect in this audit's own FINDING-006 repair, found by the fuzz

### FINDING-013 — the escape ceiling could emit a raw ESC — **HIGH**

**Location:** `src/escape.cyr` — `_emit_file_byte` (extracted from
`src/main.cyr` at 1.4.7).

**Issue.** FINDING-006's fix bounded a stripped sequence two ways, and both
bounds "abandon the sequence and emit the byte that tripped it". For the
newline bound that is correct — an LF is content and must reach the gutter.
For the byte ceiling it is not: the tripping byte can itself be `0x1B`.
When it is, owl wrote a raw ESC to the terminal and then treated the bytes
after it as ordinary content, handing the terminal a live escape
introducer. That is precisely the injection FINDING-001 exists to prevent,
re-opened by the repair for FINDING-006.

**Reachability.** Requires the ESC to land *exactly* on the byte that trips
the ceiling — with `ESC_MAX_LEN = 256`, that is 254 padding bytes after
`ESC [` (the `ESC` and `[` spend the first two of the budget). Off-by-one
in either direction and the state-0 handler catches the ESC correctly. A
hand-written test file misses it unless you compute the offset; the fuzz
harness found it because it walks the boundary.

**Repro** (254 is load-bearing):

```
python3 -c "open('f','wb').write(b'\x1b[' + b'3'*254 + b'\x1b]52;c;cHduZWQ=\x07TAIL\n')"
owl --color=always f | cat -v
```

- 1.4.6: `^[]52;c;cHduZWQ=^GTAIL` — a raw ESC and a complete OSC 52
  clipboard-write sequence delivered to the terminal.
- 1.4.7: `TAIL` — clean, 0 ESC bytes.

**Fix.** At the ceiling, an ESC begins a *new* sequence rather than being
emitted:

```
if (c == 0x1B) { g_esc_state = 1; g_esc_len = 1; return 0; }
```

An ESC is never content, so there is no case in which emitting one is the
right answer. The newline bound is unaffected — an LF cannot be an ESC.

**Process note, which is the more useful half of this finding.** The
harness did not catch this on the first try. Two earlier drafts of the
bounded-suppression invariant **passed against a build with the ceiling
deleted**: the random byte distribution emitted newlines (which reset the
machine via the other bound), and then — after that was fixed — emitted
ESCs (which legitimately restart the budget). Both drafts read like
coverage and proved nothing. The invariant only acquired teeth once the
ceiling round was made deterministic: open with `ESC [`, then feed *only*
CSI parameter bytes, so nothing in the stream can terminate the sequence or
restart the budget and `ESC_MAX_LEN` is the sole exit. The harness now
also asserts that the ceiling actually fired, and fails loudly if it did
not — a test that cannot prove it exercised its own subject should say so
rather than pass.

Every invariant is A/B-verified against a deliberately broken classifier;
see §Verification.

## Informational

### INFO-001 — `CLAUDE.md` misstates the pager execution model — **doc corrected**

§Security Hardening claimed:

> Pager spawn sanitizes environment: `OWL_PAGER` / `PAGER` values are passed
> as argv[0], never shelled-out

The code does the opposite, and deliberately: `start_pager` runs
`execve("/bin/sh", ["/bin/sh", "-c", cmd], envp)` so that flag-carrying
values like `PAGER="less -R"` work — the same contract `git`, `man` and
`less` itself offer. That is a defensible design (the variable is set by the
user, who can already run commands), but a security-posture document that
describes the opposite of the code is worse than no document: it would let a
future reviewer "restore" an invariant that never held, or trust a boundary
that is not there. Corrected in `CLAUDE.md` to describe what the code does and
why, and to state the invariant that *is* load-bearing — that owl never
interpolates a **path** or any other file-derived string into that command.

### INFO-002 — Environment input is silently ignored past 8 KB — **upstream (cyrius)**

The cyrius stdlib's `getenv` (`lib/io.cyr`) reads `/proc/self/environ` into an
8 KB buffer and scans only that. Any variable that falls beyond the window is
invisible. Measured on owl:

```
NO_COLOR=1, small environment -> 0 ESC bytes in output   (honoured)
NO_COLOR=1, environment >8 KB -> 18 ESC bytes in output  (ignored)
```

`OWL_PAGER`, `PAGER`, `HOME`, `XDG_CONFIG_HOME` and `OWL_CONFIG` are affected
the same way. Not repaired here: `lib/` is generated and owl must not carry a
private `getenv` that diverges from every other cyrius consumer — the fix
belongs in `lib/io.cyr`. Filed for the cyrius repo.

Worth stating plainly, because it bounds what the rest of this report can
promise: **owl's escape-stripping guarantee does not depend on this.**
`_strip_active()` keys off `g_want_color`, which resolves from TTY detection
rather than the environment, so a truncated environment cannot silently
disable stripping. It can only fail to *enable* `NO_COLOR`, which errs toward
more decoration, not toward passing file-origin escapes through.

### INFO-003 — 8-bit C1 control bytes are not stripped — **accepted**

The classifier triggers on ESC (`0x1B`) only. A terminal in 8-bit mode
interprets `0x9B` as CSI, `0x9D` as OSC, `0x90` as DCS directly, so a file
carrying those raw bytes bypasses the filter.

**Deliberately not fixed.** In UTF-8 — which is what every modern terminal
runs, and the only mode in which owl's box-drawing frame renders at all —
`0x80–0x9F` are continuation bytes, not controls. Stripping them would
corrupt every non-ASCII file owl displays, which is a certain harm traded
against a risk that requires a terminal in a non-UTF-8 8-bit locale. `less`
and `bat` make the same call. Revisit only if owl ever grows an explicit
non-UTF-8 mode.

## Discarded at the repro stage

Two candidates looked like findings on inspection and did not survive a
repro. Recorded because the reasoning is the useful part.

- **`_stream_grow` duplicate symbol (vyakarana vs sankoch).** The two
  definitions have incompatible signatures *and* struct layouts, and the
  build warns `duplicate fn … last definition wins`. A minimal three-file
  repro showed cyrius rebinding *all* call sites to the last definition,
  which would mean vyakarana's streaming tokenizer calling sankoch's
  function. Testing it on owl directly refuted that: a build with sankoch's
  body re-inserted last produces byte-identical highlighted output at 2/4/8/40
  KB, and an `exit 42` probe placed in the winning definition **never fires**.
  Call sites inside `lib/vyakarana.cyr` bind to vyakarana's own definition
  regardless of which one the warning names. Already recorded in
  `state.md` §Binary; unchanged by this audit.
- **`detect_language_from_shebang` index underflow.** `while (si <= sblen -
  h_len)` looks like an unsigned-underflow walk when the hint is longer than
  the shebang line. Cyrius values are signed i64, so the comparison is simply
  false and the loop does not run. No repro possible.

## Verification

Every repair carries a behavioural gate in `scripts/smoke.sh`, and every gate
was proven non-vacuous by running it against the 1.4.5 binary built from
commit `5506ddb`. Neutralising each gate in turn so the next one can run:

```
neutralised first 0 -> FAIL — FINDING-006: unterminated CSI suppressed the file (0 of 442 bytes)
neutralised first 1 -> FAIL — FINDING-006: gutter desynced after a stripped escape
neutralised first 2 -> FAIL — FINDING-007: oversized XDG_CONFIG_HOME was not rejected
neutralised first 3 -> FAIL — FINDING-008: theme colour produced a 26-byte SGR (buffer is 16)
```

FINDING-010's gate distinguishes the same way (`--tabs=65` and a 20-digit
value both exit 0 on 1.4.5, exit 2 on 1.4.6).

**Addendum (1.4.7).** FINDING-013 carries both a smoke gate and a fuzz
invariant, each A/B-verified against a classifier with the specific guard
removed — mutating the *ceiling* block precisely, not the identically
indented ESC check in the state-0 handler, which an earlier attempt hit by
mistake and which produced a misleading result:

```
mutation          fuzz result
no-ceiling     -> FAIL: classifier latched past ESC_MAX_LEN (FINDING-006)
no-lf          -> FAIL: LF dropped in state 1
esc-at-ceiling -> FAIL: ESC was emitted (FINDING-001)
unmodified     -> PASS (5 invariants)
```

and the smoke gate: `FINDING-013 regression: 1 raw ESC byte(s) reached
stdout at the escape ceiling`.

Full suite at 1.4.6: `cyrius test` 7 passed / 0 failed; `sh scripts/smoke.sh`
green; `cyrius lint src/*.cyr` unchanged from the 1.4.5 baseline; host,
`--agnos`, and both DCE builds clean; plain mode byte-identical to `cat`
across the audit corpus (including every hostile input above).
